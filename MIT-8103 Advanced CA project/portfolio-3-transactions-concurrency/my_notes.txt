1. BIG PICTURE - WHAT IS THIS PORTFOLIO ABOUT?
---------------------------------------------------------------------
In simple terms, Portfolio 3 is all about moving money safely between
wallets without losing money, double-spending, or freezing the database.

When hundreds of people transfer money at the exact same second:
- Two people might try to spend the same money at the same time.
- Two transactions might lock each other and cause a deadlock freeze.
- A network error might make a user tap "Pay" twice.
- A server might crash halfway through a transfer.

This portfolio shows how PostgreSQL transactions, row-level locks,
isolation levels, double-entry bookkeeping, and ordered locking solve
every single one of these problems.


2. SCRIPT-BY-SCRIPT BREAKDOWN (WHAT EACH FILE DOES)
---------------------------------------------------------------------
* 01_transfer_function.sql
  - The main money-moving function: transfer_funds().
  - It moves money from wallet A to wallet B as ONE complete atomic unit.
  - First, it checks the idempotency key so repeat clicks don't double charge.
  - Second, it locks BOTH accounts using LEAST(id1, id2) and GREATEST(id1, id2).
    Because every session locks in the exact same order (smaller UUID first),
    two transfers can never deadlock each other.
  - Third, it reads the sender's balance AFTER holding the lock, checks if
    there's enough money, and updates both accounts.
  - Fourth, it writes two ledger lines (one DEBIT, one CREDIT) using real-time
    clock_timestamp() so statement timelines stay accurate.
  - It also includes a broken version called transfer_funds_unordered()
    which locks sender-first and adds a tiny sleep. This was made only to
    prove how easily deadlocks happen without ordered locking.

* 02_demo_setup.sql
  - Creates two demo users: "Demo Alice" (account 9000000001) and
    "Demo Bob" (account 9000000002).
  - Puts 500.00 into each account.
  - These are separate disposable accounts so we can test locks and deadlocks
    without messing up the real 400,000+ financial ledger lines.
  - We can re-run this anytime to reset their balances back to 500.00.

* 03_commit_rollback_demo.sql
  - Runs 5 real-life payment scenarios:
    1. COMMIT: Transfer 100.00, commit it, and show the change is permanent.
    2. ROLLBACK: Transfer 100.00, change our mind, rollback, and show the
       money never moved and the transaction row disappeared.
    3. Failure Rollback: Try sending 999 million (insufficient funds). The
       database throws an error and rolls back cleanly with zero balance change.
    4. Idempotency: Send the exact same transfer call twice with the same key.
       The database returns the original transaction ID without taking the money twice.
    5. SAVEPOINT: Start a transaction, do a 10.00 transfer, set a savepoint,
       try a failed 999 million transfer, rollback to the savepoint, and commit.
       The 10.00 transfer survives while the bad transfer is discarded!
  - Finishes by querying the latest ledger lines to prove every debit has a credit.

* 05_stress_ordered.pgbench
  - A benchmark script that tests the safe transfer_funds() function.
  - Takes 20 active accounts and makes concurrent clients randomly transfer
    amounts between them over and over.
  - Because it uses ordered locking, it handles heavy contention with 0 deadlocks.

* 06_stress_unordered.pgbench
  - The exact same benchmark workload, but calls transfer_funds_unordered().
  - Because locks are acquired in random sender-first order, concurrent opposite
    transfers immediately deadlock.

* 07_integrity_check.sql
  - The financial audit script. Run before and after stress tests.
  - Checks 5 golden rules:
    1. Conservation of money: total money in system must stay exactly 10 billion.
    2. Stress transfer count: every success transfer must have exactly 2 ledger lines.
    3. Balanced transactions: total debits minus total credits must be 0.
    4. Ledger match: account balance must equal the sum of its ledger lines.
    5. Stuck transactions: no stress transaction should stay stuck in 'PENDING'.

* 08_own_experiment_reversal.sql
  - My own experiment: a safe, atomic reverse_transfer() function.
  - Undoes a completed transfer without deleting anything (financial ledgers
    must be append-only for audits).
  - Locks the original transaction row to prevent double reversals.
  - Verifies the original was SUCCESS and hasn't already been reversed.
  - Checks the receiver actually has enough balance to return the money.
  - Locks both accounts in ordered order (LEAST/GREATEST).
  - Posts mirror ledger entries (DEBIT the receiver, CREDIT the sender).
  - Marks original transaction as REVERSED and logs the new reversal transaction.

5. QUICK EXPLANATIONS OF HARD CONCEPTS (IN PLAIN WORDS)
---------------------------------------------------------------------
- ACID:
  * Atomicity: All or nothing. If anything fails, the whole transfer cancels.
  * Consistency: Rules are never broken (no negative balances, total money stays same).
  * Isolation: Concurrent transfers don't mess up each other's view of data.
  * Durability: Once committed, a power cut won't wipe the transaction out.

- Ordered Locking:
  If Alice sends to Bob, and Bob sends to Alice at the same time:
  Without ordering: Alice locks Alice then waits for Bob; Bob locks Bob then waits for Alice. Deadlock!
  With ordering: Both transfers MUST lock the lower ID first, then the higher ID.
  One gets the first lock, the other waits politely. No cycle, no deadlock!

- Idempotency:
  Giving every payment a unique key. If your internet stutters and the app retries,
  the database recognizes the key and says "I already did this, here is your receipt",
  instead of charging you twice.

- Savepoints:
  Like checkpoints in a video game. If a mini-step fails, you can jump back to the
  checkpoint without losing everything you did since starting the level.

- Append-Only Ledger:
  In banking, you NEVER use "DELETE FROM transactions" or "UPDATE balance" to fix
  a mistake. You post a new reversal entry. That way an auditor can trace every
  single cent from day one.
